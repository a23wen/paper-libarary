## 研究背景

一个研究助手在第一次处理电子表格时，可能反复手写查找逻辑、误判空值，再花几轮修复。第二次面对同类表格，如果它只能读取上次的对话，就仍需临时恢复这套经验；如果它能够保存并复用验证过的处理函数，下一次执行的起点就改变了。

这类适应发生在模型权重之外。论文把包围模型的提示、上下文构造、记忆、工具、调度与执行基础设施统称为 **harness（智能体运行框架）**。模型负责推理和生成，harness 决定模型看见什么、能调用什么，以及运行结果怎样被记录和影响后续任务。

现有工作已经覆盖反思文本、技能库、工作流搜索以及整套智能体代码修订，但这些系统常被笼统称为“自我改进”。本文试图先建立共同语言：**到底修改了哪个对象，修改如何产生，什么证据足以让它进入后续运行？** 把三件事拆开，才有可能比较不同系统的能力与可靠性。（§1–3，PDF 第 2–5 页）

## 问题与挑战

**因为程序修改会改变后续输入与执行路径，一次局部修复可能同时改变多个任务的行为。** 修改记忆检索函数可能帮助长对话，却也改变代码智能体获得的项目约束；两个单独有效的插件合并后，可能因共享状态而相互干扰。因此，修改行数少、接口不变，都不能直接推出行为变化小。

**因为候选是在反馈上反复搜索出来的，验证分数会逐渐参与优化。** 如果每次看见验证失败就针对性修改，同一组“保留集”最终也成了开发信息。更高的已见任务分数，不能自动说明在未见任务上更好。

**因为持续学习既要适应新任务又要保留旧能力，平均收益可能掩盖局部退化。** 例如办公任务准确率上升，同时代码恢复能力下降；总体均值可以变好，但某一用户群的体验仍然恶化。泛化、历史能力保留和候选准入需要分别处理。

## 核心发现 Finding

### 作者明确声称：自演化是过程，自改进是需要比较证据的结果

论文定义中的自演化至少有两项要求：

1. **使用自身运行反馈，并保留继续更新的机制。** 不是人工一次性写好提示后永远不变。
2. **被接受的修改会跨运行持久化。** 后续任务实际加载修改后的状态。

因此，按固定规则追加日志或压缩上下文，并不自动构成 harness 自演化；从反馈中形成可复用程序，或修改记忆管理策略，才可能满足定义。一次观测到的更新也可以展示这种能力，但前提是系统确实具备上述持续机制。它不要求每次更新都成功。（§2，第 2–3 页）

### 我的理解：关键不是“让智能体改代码”，而是建立可检验的经验继承链

这篇论文最有用的新视角，是把系统拆成 **运行 → 反馈 → 修改提议 → 独立评估 → 持久采纳 → 再运行** 的链条。一个程序被生成、被存进档案、被投入运行，以及被证明有用，是不同事件。

以表格助手为例，保存一个新查找函数只证明产生了可复用对象；后续任务必须真的调用它，输出质量还要保持，才能讨论复用收益。若只是少调用了几次工具，但总时间和 token 增加，就不能直接称为效率提升。这个区分将工程上的“能改”转化为研究上的“为何可采纳、改进是否成立”。

## 方法

本文的方法是**统一建模与分析框架**，并非一套新模型训练算法。

### 1. 固定模型，明确可修改对象与最终评价边界

用 `M` 表示模型，`H` 表示 harness，`E` 表示任务环境，运行产生轨迹 `τ`，最终评价器 `J` 给出结果：

```text
τ ~ Run(M, H, E)
y = J(τ)
```

候选可以修改 harness 内部的临时检查或内部 critic，但不能修改最终决定成绩的 `J`。否则“通过检查”可能只是改变了检查规则。论文把模型适配器归入 harness，把学习得到的参数归入模型。（§2，式 1、表 1）

### 2. 从运行批次中提出修订，通过采纳机制更新

每一轮先用当前 harness 在一批任务上运行，收集轨迹、结果与反馈；更新过程进行诊断、产生候选、评估并决定采纳。没有候选获准时，继续沿用旧版本。档案、历史反馈和额外验证运行都可以参与这一过程。（式 2–3）

这解释了为什么“档案中保留一个候选”不等于“部署更新”：只有后续执行切换到该候选，才改变了持续运行的系统。

### 3. 根据修改对象分类，而非根据文件扩展名分类

| 修改对象 | 具体含义 | 示例 |
|---|---|---|
| 解释性状态 | 修改由既定能力解释的指令、经验或任务级编排 | 改提示、整理记忆条目、重排固定算子的流程 |
| 工具与组件实现 | 修改可调用函数或指定模块内部实现 | 改写记忆管理函数、增加一个表格工具 |
| 仓库级运行控制 | 修改上下文构造、循环、恢复、终止等组件间控制 | 工具失败后如何恢复，何时停止运行 |
| 插件组合 | 修改组件或运行时服务的绑定、依赖与装载方式 | 替换记忆后端，将新能力挂载到执行系统 |

仅用 Python 组合既有算子，仍可能是解释性工作流；改变执行这些算子的机制，才是可执行修订。插件组合也可能同时涉及组件实现和仓库控制，因此这些类别并不互斥。（§3，第 3–5 页）

### 4. 用演化搜索描述候选产生与选择

论文从可变状态表示、变异、适应度评估和保留规则四个角度理解 harness 搜索。Figure 2 对照了单候选精英搜索、多候选搜索、档案搜索、重组、质量多样性、组件协同、多目标选择和 bandit 预算分配。

这里是**结构上的对应关系**，不表示每个智能体方法都完整实现了某种经典演化算法。例如，把几份程序合并不自动构成严格的遗传编程；用成本与性能选候选，也不代表已经实现了完整的多目标演化算法。（§4.1、Figure 2，第 6 页）

### 5. 将三种可靠性结论分别写清楚

**期望泛化差距。** 在任务按轮次内与轮次间独立采样、模型和评价器固定、损失位于 `[0,1]` 等条件下，替换一个历史任务并重新运行所有后续更新，可以用完整更新过程的稳定性量 `β` 约束期望泛化差距的绝对值。它约束的是 `|E[真实风险 − 经验风险]|`，不是每一次运行的差距，也不是“少改几行代码就泛化”。（§4.2，式 4–5，第 7 页）

**历史能力保留。** 如果每一步在历史分布上的风险增加都不超过预先指定的预算 `ε`，那么多轮之后的退化不超过这些预算之和。证明的关键是对逐步风险差做望远镜求和。历史回归预算是额外假设，不是稳定性自动带来的结果；局部验证也不能替代合并后的整套系统验证。（式 6）

**独立验证准入。** 每轮先固定最多 `K` 个候选，再从历史任务分布的均匀混合中抽取 `m` 个新的独立任务，对候选和当前版本作成对比较。若一共比较 `T` 轮，由 Hoeffding 界与 union bound，所有候选的风险差同时以至少 `1−δ` 的概率满足：

```text
真实风险差 ≤ 观测平均风险差 + sqrt(2 × ln(KT/δ) / m)
```

这里风险差是“候选减旧版本”，负数才表示改进。只接受右侧小于 0 的候选。成对损失差范围为 `[-1,1]`，这决定了上界中的系数。（式 7–8，第 7 页）

**一个说明性计算，并非论文实验：** 若 `K=10、T=20、δ=0.05、m=1000`，不确定性项约为 `0.129`。即使观测到风险下降 `0.05`，这个保守上界仍不能认证改进。反复运行同一批任务可以降低执行噪声，却不会把独立任务数从 1000 变成 10000。

如果依据本轮验证结果再次编辑或合并候选，新版本需要重新获得独立验证，或采用允许自适应复用数据的统计方法。总体历史混合分布变好，也不保证每个历史子群都不退化。若评价器损失与真实目标风险之间存在至多 `η` 的偏差，还需在准入上界中加上 `2η`；这个偏差必须有证据支持。（式 9，第 8 页）

## 实验与结论

### 本文提供案例证据，没有新建统一 benchmark 对照实验

短文的经验材料主要引用已有工作，用来说明模型与 harness 的配合、插件生成的前期成本，以及复用和部署的权衡。不能将这些案例表格说成本文作者独立复现的跨系统评测。

### 代表案例：模型与 harness 的组合可以改变性能排序

Table 2 转述 Shen 等人的 SpreadsheetBench 结果，指标为准确率百分比；HarnessOpt（HO）将修改范围从 skill 扩展到预览、输出检查和失败恢复等运行时逻辑。（§3.2、Table 2，第 4 页）

| 模型 | 初始 | SkillOpt | SkillOpt-Lite | HO only | HO + skill |
|---|---:|---:|---:|---:|---:|
| GPT-5.4-nano | 29.89 | 51.60 | 66.19 | 76.51 | 77.58 |
| GPT-5.4-mini | 28.21 | 47.50 | 73.31 | 81.14 | 82.56 |
| GPT-5.4 | 39.86 | 61.50 | 79.36 | 83.63 | 85.05 |
| GPT-5.5 | 37.37 | 76.20 | 79.72 | 83.63 | 85.77 |

代表性比较是：GPT-5.4-nano + HO + skill 达到 **77.58%**，高于 GPT-5.5 + SkillOpt 的 **76.20%**。它说明模型排序可以随 harness 配置改变，研究系统能力时应同时记录两者。但这是不同模型与不同优化配置的交叉比较，**不能推出相同总成本下小模型普遍优于大模型**。

同一模型下，HO + skill 相比 SkillOpt-Lite 提高 **5.69–11.39 个百分点**；这支持把运行时也纳入优化范围的价值。至于哪个具体组件造成多少收益、适应阶段花费多少，不能仅凭这张转述表回答。

### 工具调用变少，为什么第一轮仍然更贵？

EIP 插件案例中，首个表格任务的工具调用从 **13 次降为 3 次**，但 token 从 **41,119 增至 47,572**，墙钟时间从 **15.49 秒增至 24.00 秒**。生成可复用工具有前期开销，所以调用次数并不是成本的充分指标。（§3.3、Table 3，第 5 页）

同一来源另报累计复用序列：从第二个任务开始出现节省，五个任务累计差为 **−110,351 tokens、−22.97 秒**。作者特别指出，首任务明细算出的增量是 **6,453 tokens、8.51 秒**，但累计序列第一行写 **4,895 tokens、6.74 秒**。两者未对齐，**不能把它们拼成一条精确的累计成本曲线**，也不能据此确定普遍的回本任务数。

Table 4 还转述 LiveBrowseComp：XYZ + dsh-everything 为 **51.39**，XYZ-Aquila-mini 为 **48.7**。原文明确说分数单位未说明，因此这里不加百分号；缺少匹配预算、匹配任务质量和重复运行，不能将差异直接归因于插件自演化。（第 5–6 页）

### 其它案例与可成立的结论

Figure 3 引用既有客户端—边缘协同推理研究，在该工作负载和 **100–500 KB/s** 通信条件下，协同方案延迟最低。它是固定部署的通信权衡案例，不是一次 harness 演化实验。（§6.2，第 9 页）

这些材料共同支持一个研究方向：应将适应成本、后续执行成本、任务质量、旧能力保留与跨环境迁移放到同一个评估设计中。本文的理论说明这种评估需要哪些假设；它没有证明任意自修改智能体都会持续变强。

## 局限与研究启发

**理论的适用边界很明确。** 独立任务、新鲜验证、固定评价器和有界损失是结论的条件。真实系统中的相关 session、分布漂移、自适应复用和非加性指标，需要额外分析。历史分布上的证书也不覆盖任意未来分布。

**工程上可回滚，不代表后果完全可逆。** 论文在个人工作区、企业流程、科研、机器人和公共服务五类场景讨论持久修改的传播。对研究者而言，这要求同时记录代码、技能、记忆、缓存以及实际生效的版本；仅保存 Git 提交未必能还原整个状态。（§5–6）

**我的研究启发：** 做 harness 或 rubric 优化时，可以先把实验记录拆成四项：提议数据来自哪里、采纳数据是否独立、最终报告使用什么测试集、部署的到底是哪份组合。若评分规则也在演化，还要固定独立的最终目标测量，避免把更容易获得的评审分当作真实任务改善。

一个可执行的后续实验是：固定模型与推理预算，比较原 harness、优化后冻结的 harness、转移到新任务的 harness，以及在新任务上继续演化的 harness；同时报告每组旧任务回归、优化成本与实际组件调用。这样的设计比只展示最后一个最高分更能回答“积累了什么能力”。这是基于本文框架的实验建议，并非作者已完成的结果。

## 关键术语

- **Harness（智能体运行框架）**：决定模型输入、工具、记忆与执行流程的软件及配置。例子：选择把完整搜索历史还是压缩后的证据清单提供给模型。
- **Harness Self-Evolution（运行框架自演化）**：利用执行反馈持续修订并跨运行保存 harness。例子：从失败轨迹中改进恢复函数，下次任务加载新函数。
- **Interpreted State（解释性状态）**：由已有执行机制读取的提示、经验或任务级配置。例子：新增“读取表格前先检查表头”的技能说明。
- **Executable Revision（可执行修订）**：改变工具实现或实际运行控制。例子：修改解析表头的函数，而不只是修改说明文字。
- **Admission（采纳准入）**：决定候选是否替换当前部署版本。例子：新函数在独立任务上通过比较后，才进入默认工具库。
- **Algorithmic Stability（算法稳定性）**：替换一个样本后，完整更新过程产生的行为变化有多大。例子：删去一次偶然失败是否导致后来所有版本走向完全不同的策略。
- **Retention（能力保留）**：新更新后维持旧任务表现的能力。例子：增加表格技能后，原有代码修复任务不显著退化。
- **Adaptive Data Reuse（自适应数据复用）**：根据数据反馈继续选择或修改候选，再用相同数据评估。例子：每次依据同一验证集的失败项修复后，又把该验证分当成独立证据。
