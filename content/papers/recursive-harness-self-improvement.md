## 📋 论文概述

如果让多个 coding agent 合作完成一个研究项目，增加“研究员、工程师、审稿人”等角色并不会自动形成可靠协作。数据处理智能体可能没有留下可核查的划分记录，训练智能体可能用了不同版本的数据，报告智能体又可能把未显著的结果写成显著。每个人都做了工作，最后交付物仍然互相矛盾。

这篇论文问的是：**固定基础模型，只让系统根据自己上一次的交付结果修改协作规则，能否比单纯提高推理强度更有效？**

作者提出 Recursive Harness Self-Improvement，简称 **RHI**。它把 harness 写成一段可修改的提示词，规定各智能体的角色、任务、输出接口和协作顺序。每轮重新执行同一任务，把新旧仓库交给 LLM 裁判比较，再用累计的比较反馈修改下一版 harness。

本文阅读的是 **arXiv:2607.15524v1**，arXiv 提交日期为 **2026-07-17**，PDF 首页另标 **2026-7-20**；作者来自 Sakana AI 与 UC Berkeley。以下页码均指这一版 PDF 的页码。论文页未标注正式录用会议，截至阅读日未从论文或作者来源核实到官方代码仓库，因此保留代码字段为空。[论文信息与版本](https://arxiv.org/abs/2607.15524v1)

## 🎯 研究背景

### 从提高模型能力，到改善模型如何工作

模型能力通常通过更大训练规模或更多推理计算提升。但 coding agent 还依赖模型之外的执行系统：怎样调用工具、什么时候拆分任务、如何共享文件、由谁检查结果、失败后如何返工。

论文将这些机制统称为 **harness**。它不只是输入模型的一句指令，也包含驱动模型持续行动的循环。模型相同，循环不同，实际效果可能不同。

已有的 harness 或工作流优化方法会维护候选集合、生成多个修改分支，然后运行任务选出较好的版本。对于一个需要生成代码、训练模型和撰写报告的开放任务，每次候选评估都要重新执行完整项目，成本很快变高。RHI 把搜索范围收紧到单条修订路径，希望用少量迭代就得到可用的任务专用工作流。[§1–3，PDF pp.3–8](https://arxiv.org/pdf/2607.15524v1#page=3)

### 本文只做模型与 harness 共演化的前半环

作者的长远设想是：更好的 harness 产生更高质量的执行轨迹，这些轨迹再用于训练下一代模型。**本文实际验证的是固定模型时改善 harness 与生成产物，未把轨迹用于基础模型再训练。** 因此，不能把结果写成“已经证实持续训练收益”或“模型权重实现递归自我改进”。

## ⚠️ 问题与挑战

### 1. 因为开放任务没有单一正确答案，优化反馈容易混杂

一个研究仓库既要符合题目，又要有正确实现、可靠数值、可运行入口和一致的报告。它无法像一道数学题那样只检查答案是否等于标准值。

RHI 采用多维度成对偏好评价，但这也意味着反馈取决于裁判看到哪些材料以及如何权衡。报告写得更完整，不必然表示代码真的更正确；材料齐全，也不必然表示研究结论可复现。

### 2. 因为每次评估都要执行项目，广泛搜索很贵

在每轮同时比较多个 harness，可以降低走错方向的概率，却需要生成多个完整仓库。RHI 每轮只新执行一个版本，并复用前一个版本的缓存产物，节省搜索调用数，但也减少了探索范围。

### 3. 因为协作失败发生在交接处，单独强化角色不够

“训练专家”这个角色名没有说明数据划分由谁冻结，结果该以哪个 JSON 字段交付，报告出现矛盾时该召回谁。缺少这些接口约定，更多智能体可能带来更多上下文传播和重复劳动。

因此，作者优先改的是 **contracts 与 hops**：前者规定传递什么，后者规定下一步由谁做什么，以及何时返回前一步修正。

## 🔍 核心发现 Finding

### 作者明确声称

作者认为，少量任务内 harness 修订可以提高固定模型在该评估协议下的表现；提升主要与更有效的任务专用上下文管理和智能体间信息流有关，而不只是生成更长的输出。论文中的 `high` 是相对于 `xhigh`、`max` 或 `ultracode` 的较低配置，不能把它误写为产品实际名为 `low` 的推理档位。[§5，PDF pp.12–16](https://arxiv.org/pdf/2607.15524v1#page=12)

### 我的理解：可优化对象是协作中的信息边界

这篇论文最有用的视角是：**智能体协作质量取决于信息如何被整理成下游可消费的证据，而不只取决于每个参与者单独想了多久。**

例如，训练智能体若只说“模型训练完成，结果不错”，报告智能体必须重新搜索文件、猜测主要模型，再自行判断统计结论。若通信契约要求返回：

- 使用的数据划分文件；
- 训练配置与模型标识；
- 指标 JSON 的路径和关键字段；
- 运行命令、退出状态与未解决问题；

那么下游可以直接核查事实。再加上“报告与指标冲突时召回训练智能体”的工作流，错误便有了明确修复路径。

这个例子是对机制的解释。论文的 embedding 分析与缓存成本变化支持这种解释，但**没有通过分别冻结或删除 contract、hop 的严格干预实验证明它们贡献了多少性能提升**。作者也明确把相关分析称为诊断性、相关性的证据。

## 🔬 方法

### 1. 把 harness 表示为结构化文本

RHI 不要求访问黑盒 coding agent 的底层代码。它把原任务 `x` 扩展为 `x + H[i]`，其中 `H[i]` 是第 `i` 版 harness。基础模型、裁判与 harness 优化器保持固定，修改的是这段文本。

| 组成 | 回答的问题 | 具体例子 |
|---|---|---|
| Role | 谁负责 | 数据处理者、模型实现者、独立验证者 |
| Instruction | 需要做什么 | 按指定划分训练，报告缺失值与失败情况 |
| Contract | 向主控交付什么 | 指标文件路径、字段 schema、命令和检验记录 |
| Hop | 何时调用谁 | 数据审查通过后才训练；证据冲突时重新委派 |
| Auxiliary rules | 何时结束或降级 | 验收门槛、失败回退、基于证据的召回条件 |

图 3–4 将前两项视为 agent design，将 contract 和 hop 视为 agent workflow。优化器提示词明确要求优先加强输出接口与主控和子智能体之间的反馈循环。[§3.3，PDF pp.9–10；附录 C，p.67](https://arxiv.org/pdf/2607.15524v1#page=9)

### 2. 运行、比较、记忆、修订

图 2 与 Algorithm 1 的主循环可以概括为：

```text
同一个任务 x + 当前 harness H[i]
    → coding agent 生成仓库 y[i]
    → 裁判比较 y[i] 与上一版 y[i-1]
    → 将胜 / 负 / 平和比较反馈加入历史 D[i]
    → harness 优化器依据当前设计与历史生成 H[i+1]
    → 在下一轮重新执行任务
```

历史不是只保留最近一轮。早期出现过的缺陷可以持续影响后续修订，减少一次噪声反馈直接抹掉旧经验的风险。论文将其称为一种语义层面的 momentum；这里没有常规梯度，也没有参数 EMA。

算法用所有任务中新版本胜过前版本的比例作为 improvement rate，低于给定阈值时停止。正文给出这一停止规则，但没有在实验配置中清楚列出实际阈值，复现时需要补充。[§3.1–3.2，PDF pp.6–9](https://arxiv.org/pdf/2607.15524v1#page=6)

### 3. 优化器实际看到的反馈，比“一个胜负标签”丰富

正文的简写是 `H[i+1] = L_harness(H[i], D[i])`。但附录 C 的实际提示还包含：

- 原任务与当前多智能体设计；
- 当前仓库的目录树和交付物存在性检查；
- 报告、指标 JSON、依赖与部分代码摘录；
- 历史胜负、裁判理由、反复出现的问题汇总；
- 要求说明修改内容、所用证据、预期机制和下一轮验证办法。

所以它属于**产物证据与偏好历史共同驱动的文本优化**，不能描述成仅凭一个二元标签就发现了协作机制。

附录给出的一个反馈例子指出：报告将 `p=0.122` 的结果描述为显著，且正文声明的主要模型与指标文件不一致。此时优化器可以新增“报告中的主模型名称与 JSON 必须一致”的交付契约，以及“写作前独立核对数值”的检查步骤。这个例子来自论文展示的反馈材料，不能当作整个基准上的错误发生率。[附录 C，PDF pp.67–70](https://arxiv.org/pdf/2607.15524v1#page=67)

作者强调，完整评价提示 `x_eval` 不直接提供给优化器；但评价标准仍会通过裁判理由和偏好历史间接进入优化。因此这是偏好驱动的适应，不是完全隔离于评价信号的无监督过程。

### 4. 为什么只和上一版比较可能有效

原始理想目标是让一个 harness 胜过广泛的竞争者；RHI 改为让它胜过自己的前一版。作者明确说明，后者**不是原全局目标的无偏估计**。

理论论证依赖一个假设：每个 harness 存在任务效用 `u(H)`，两者之间的胜率是效用差的严格单调函数，且效用相同时胜率为 `1/2`。再假设竞争者分布不随候选改变，那么局部和总体胜率都按同一个效用排序。于是，真实胜率超过 `1/2` 的修改可以提供局部上升信号。

但一次裁判判胜不等于真实胜率超过 `1/2`；若偏好不传递、不同指标互相冲突，或裁判有偏，假设就可能失效。这段论证不是全局最优或每轮单调改进的收敛保证。

表 1 的 `Θ(1)` 也应按其计数方式理解：每轮一个新执行加一个新成对比较，前版产物缓存复用。它没有把执行时长、历史变长、优化器调用等全部化成同样成本；表内对 population 的平方比较数采用了全配对方案，不能据此断言所有种群搜索算法都必须支付平方成本。[表 1 与局部效用论证，PDF pp.7–8](https://arxiv.org/pdf/2607.15524v1#page=7)

## 🧪 实验与结论

### 1. 实际评估的是怎样的任务

基准有 **30 个合成、开放式 ML 研究任务**：量化金融、机器人、药物领域各 10 个。任务由 LLM 根据相关招聘岗位描述改写而来，要求 agent 生成完整研究仓库。

通用交付物包括研究报告、PNG 图、`metrics.json` 和列出文件路径的 `index.json`；部分任务另要求模型对照、消融结果或可运行脚本。这里的“合成”指任务提示的构造方式，不表示每个实验都只用合成数据。

例如，附录 B 的任务要求从 PDB 提取蛋白质结构数据，为 SE(3) 等变网络实现可复现训练，预测侧链角度，并报告角度误差及速度、显存开销。它同时涉及数据获取、几何建模、对照实验和报告一致性，正适合暴露交接问题。[§4，PDF pp.10–11；附录 B，p.33](https://arxiv.org/pdf/2607.15524v1#page=10)

### 2. 裁判看指定交付物，不是完整独立重跑

两个仓库按交付覆盖、数值与实证严谨性、可复现性、呈现、工程质量和任务对齐进行比较。输入主要取任务指定交付物与部分文件摘录，必要时对双方按相同规则截断；上下文预算约为裁判最大输入的 30%–40%。

Sonnet-4.6 与 Opus-4.8 的主结果使用两个裁判配置；Opus-4.7 的比较扩展到六个配置。主配置包括 `gpt-5.5-max` 以及 `opus-4.7-xhigh` 或 `opus-4.8-xhigh`。每个评价配置使用三个随机种子重复，报告均值和标准差。**这里的三个种子指评价重复，不能据此声称每种 coding agent 都独立生成了三次仓库。**

指标是 30 个任务上的成对胜、负、平计数，不能解释为代码测试通过率、科学发现成功率或人类专家认可率。[§4.2–5.2，PDF pp.11–13](https://arxiv.org/pdf/2607.15524v1#page=11)

### 3. 主要结果：少量修订超过同模型的更高推理配置

| 固定模型与 RHI 版本 | 对照 | 成对评价结果 | 归一化执行成本：RHI / 对照 |
|---|---|---|---:|
| Sonnet-4.6 `high + H[2]` | 同模型 `max` | 正文报告赢得 30 次比较中的 20 次 | 2.38 / 2.56，约低 7% |
| Opus-4.7 `high + H[1]` | 同模型 `xhigh`、`max` | 一轮修订后超过这两种配置 | 对 `max` 为 2.11 / 2.60，约低 18% |
| Opus-4.8 `high + H[2]` | 同模型 `xhigh`、`max`、`ultracode` | 两轮修订后超过这三种配置 | 对 `max` 为 1.69 / 2.19，约低 23% |
| Opus-4.8 `high + H[2]` | 同模型 `ultracode` | 同上 | 1.69 / 4.15，约低 60% |

数据来自图 5–7 与 §5.3、§5.5；归一化基准分别是对应模型没有 RHI 的 `high` 执行，每个任务先归一化，再跨任务平均。不同模型行的归一化值不能直接当作美元成本比较。[PDF pp.12–16](https://arxiv.org/pdf/2607.15524v1#page=12)

Sonnet 的 `20/30` 是正文概述的胜出任务数口径；图中计数经过裁判与种子重复后汇总。分母保留全部 30 个任务，平局不计胜，不应改算成删除平局后的胜率，也不能把各次重复判断当作新的独立任务。

### 4. 代表实验细读：Opus-4.8 为什么有说服力，又能说明到哪一步

图 7（p.14）逐步展示了普通 `high`、初始 `H[0]`、一轮后的 `H[1]` 与两轮后的 `H[2]`。

普通 `high` 在成对评价中落后于更强推理配置。加入初始 harness 后已经缩小差距，但 `H[0]` 不是最终结果；继续修订两轮后，`H[2]` 才在两个裁判配置下都超过图中的 `xhigh`、`max` 与 `ultracode`。

对 `ultracode` 的比较尤其值得注意，因为这个对照本身也能使用内建的动态多智能体工作流。因此论文支持的是：**在这组任务上，用户提供并迭代修订的任务专用协作规则，可以胜过被评估的内建通用协作配置。** 它没有证明任意手写规则都优于产品内建 harness。

再看图 7e 的资源：

- `H[2]` 的归一化成本为 **1.69**，`ultracode` 为 **4.15**；
- `H[2]` 的归一化输出 token 为 **1.65**，`ultracode` 为 **3.57**；
- `H[2]` 的归一化缓存读写为 **1.69**，`ultracode` 为 **4.74**。

这些是达到该版本后执行任务的成本。**图中没有清楚列出获得 H[2] 之前所有版本执行、裁判与 harness 优化器调用的累计总账，因此“最多省 60%”不能直接改写为“从零优化到最终交付的总费用省 60%”。** 它也不代表比普通 `high` 更便宜：`H[2]` 的 1.69 仍高于基准 1.00。[图 7，PDF p.14；成本说明 p.16](https://arxiv.org/pdf/2607.15524v1#page=14)

### 5. 输出长度与性能并不同步，但结论应分模型讨论

Sonnet 的 RHI 版本输出量约在 **1.71–1.86** 之间，Opus-4.8 在 **1.42–1.81** 之间，性能却继续改善。因此，至少这两种配置的增益不能只解释为输出变长。

Opus-4.7 的输出量随性能一起增加，作者明确说该模型上的证据不足以区分两种解释。另一个限定是：上述“近似不变”指 RHI 各版本之间，不代表加 harness 后的输出量等于普通 `high`。[§5.4，PDF p.15](https://arxiv.org/pdf/2607.15524v1#page=15)

### 6. 更强基础模型的优势没有被消除

图 8 比较经过 RHI 的 Sonnet-4.6 与更强的 Opus-4.7。Sonnet 明显改善，但不能稳定填平两者差距。作者因而将 RHI 视为与基础模型能力提升互补的方法。

附录 A 还比较普通单智能体、只要求组队的默认多智能体、加明确初始 harness 的多智能体，以及把相同角色和指令交给单智能体执行。明确 harness 的多智能体表现最好，而单纯要求组队可能花更多成本、取得更低 Elo。这个对照支持协作结构有用，但仍不等于识别出 contract 和 hop 各自的独立因果贡献。[图 8，PDF p.17；图 13，pp.32–33](https://arxiv.org/pdf/2607.15524v1#page=17)

### 7. 信息论分析：一种可检验假说

作者进一步提出，RHI 的隐式更新方向可能是：

```text
增加 contract、hop 中关于当前任务的信息
    − 减少已知任务之后，各 harness 组件之间的重复信息
```

这个目标不是实际训练使用的 loss。作者将文本编码成 embedding，经白化 PCA 降至 10 维，再用高斯典型相关估计互信息，并报告打乱任务标签后的去偏估计。

表 2（p.24）中，使用 `text-embedding-3-large` 的去偏统计，从第 1 到第 4 轮：

| 组件与任务的互信息代理 | 第 1 轮 | 第 4 轮 |
|---|---:|---:|
| Role | 0.47 | 0.33 |
| Instruction | 0.99 | 1.00 |
| Contract | 0.99 | 1.34 |
| Hop | 1.96 | 2.54 |

单位为 nats。表 3（p.25）中，同一编码器下去偏的任务条件总相关从 **4.84** 降至 **3.63**；换 `all-mpnet-base-v2` 后由 **3.51** 降至 **2.62**。这些变化与“接口越来越贴合任务，同时减少冗余”一致。

但有三个关键限定：第一，embedding 统计不是原始文本信息量的精确测量；第二，优化器提示本来就明确要求修改 contract 和 hop；第三，表 3 脚注说明 hop 对同一任务和轮次的各 agent 是同一个向量，任务内中心化会将其消掉，因此该条件统计实际上主要测量 **role、instruction、contract** 的剩余依赖。不能把它当成四种组件均被完整测量后的机制证明。[§6.3、表 2–3，PDF pp.22–25](https://arxiv.org/pdf/2607.15524v1#page=22)

## 📚 关键术语

- **Harness（智能体执行框架）**：规定模型怎样执行任务、使用工具与协调工作的外部机制。例子：先并行读取数据和建模要求，再由主控整合并决定是否训练。
- **Communication Contract（通信契约）**：智能体之间约定的输出内容和格式。例子：必须提供指标路径、数据版本和实际运行记录，不能只返回“已完成”。
- **Workflow Hop（工作流步骤）**：一次调用、交接或召回。例子：验证者发现数据泄漏后，主控召回数据处理者重建划分。
- **Trajectory-local Search（沿修订轨迹的局部搜索）**：每轮主要把当前版本与紧邻的上一版比较。例子：比较 H[2] 和 H[1] 的产物，而不同时维护十个候选分支。
- **Pairwise Preference（成对偏好）**：让裁判在两个候选之间选择更好者或判平。例子：两个仓库都能生成图，但其中一个报告与指标一致，因而更受偏好。
- **Total Correlation（总相关）**：度量多个随机变量整体依赖程度的统计量。例子：若所有角色描述都重复同一套规则，它们的表示可能含有大量共同信息；但这里使用的是 embedding 上的近似诊断。
- **Model–Harness Co-evolution（模型与执行框架共演化）**：改良 harness 产生更好轨迹，再用轨迹改善模型的设想。例子：将经验证的研究执行轨迹用于后续训练；后一环尚未在本文验证。

## 💡 局限与启发

### 评价范围与证据质量

只有 30 个由 LLM 构造的研究任务，不能推断对所有软件项目或真实研究问题都成立。论文在同一个目标任务上反复修订和评价 harness，也没有证明演化规则能迁移到未见任务。

裁判读取的是指定交付物及截断摘录。附录 E 的示例还保留运行类型标签，二进制文件被省略；没有看到清楚的全程盲化与交换顺序协议。因此，双模型裁判与重复评价提高了稳健性，但不能替代独立执行验证或专家检查。[附录 E，PDF pp.73–86](https://arxiv.org/pdf/2607.15524v1#page=73)

### 成本与局部优化

“每轮一个新候选”是有用的调用数优势，但目标任务自身可能很昂贵。完整采用成本应包含初始运行、所有修订运行、评价和优化，再与同预算的重复采样、直接修改产物等策略比较。

局部比较可能陷入特定裁判偏好，也可能丢掉早期较好的设计。论文使用历史作为缓冲，但尚不足以证明它在任意噪声条件下都稳定。复现还需要补齐停止阈值、优化器具体配置和累计成本等细节。

### 可直接采用的设计建议

我的理解是，可以优先把任务中的高频交接失败变成明确接口：谁提供证据，证据存在哪里，谁核验，以及哪种失败触发返工。对于研究 agent，尤其应把“实际执行的结果”与“报告中的主张”绑定起来。

若要研究这套机制，可先做一个受控实验：固定模型、预算和任务，分别允许修改角色描述、通信契约、工作流步骤，再用独立可执行检查评价产物。这样才更接近回答“哪类 harness 修改真的改善了协作”。
